- (event) Spec folder created 2026-09-20 from owner direction; new spec rather than an in-place spec-fonts update, with spec-fonts/SPEC.md adopted as a companion and its reversed clauses amended in place (owner choice).
- (direction) Owner: allow fonts to be loaded from disk as well - today there are only two sources, the faces shipped with the core engine and the faces embedded in the .folio.
- (direction) Owner: the main template's page setup gains an option to embed fonts in the .folio or not; when not embedded and not found on disk at render time, the font falls back to the one shipped with the core engine.
- (note) Measured: a chain entry's string shape already means 'a face the renderer is given at render time (the shipped set, or one the integrator supplies)' (docs/folio-format.md); a declared face missing from the supplied set refuses the render with TEXT_FACE_ABSENT. So a non-embedded face needs no new entry shape - only a disk source feeding the FontSet, and a lenient resolution mode.
- (note) Measured: folio8.FontSet (folio-go/fontset.go) is the engine's only font input and its doc comment states the engine never goes looking for fonts on the machine it runs on; cmd/folio8 builds it from fonts.Shipped() alone (main.go:235,286).
- (note) Measured: document-level settings already travel as engine commands - setDocumentLocale and setDocumentUTCOffset - and surface in the designer's PAGE SETUP section (App.tsx:4439), which is the control the owner calls 'the main template's page option'.
- (decision) OWNER (2026-09-20, Q1): disk loading lands on BOTH sides - the author picks a font file off their own machine in the designer, AND the rendering host can load faces from disk at render time. This reverses spec-fonts D-8.6.1 (author disk import declined) and spec-fonts' FR33 constraint (nothing read at render time, no path on disk) together with its 'No host fonts' non-goal.
- (decision) OWNER (2026-09-20, Q2): a non-embedded face absent at render time FALLS BACK to a shipped face AND emits a diagnostic naming the chain, the entry and the face actually painted. This reverses spec-fonts CAP-4's 'no render produces a page set with a substituted face' - the substitution is now allowed, but never silent.
- (decision) OWNER (2026-09-20, Q3): Folio does not gate an author-supplied face on its licence - having the right licence for a font the author loads is the author's responsibility, not the product's. This reverses the reasoning D-8.6.1 declined on.
- (decision) OWNER (2026-09-20, Q4): an author-supplied embedded face fills the format's three required licence fields by COPYING WHAT THE BINARY SAYS - name ID 0 (copyright), name ID 13 (licence description) and name ID 14 (licence URL), verbatim, with no judgement. The fields stay required; an empty value is legal. The document reports the face's self-description rather than an assertion by Folio.
- (assumption) Assumed the ENGINE still never touches the filesystem: the disk source is a host-side helper that builds a FontSet from a directory the integrator names, and the engine's only change is the lenient-vs-strict resolution mode. Derived from folio8.FontSet being the sole font input and from the architecture's standing 'never queries the host' rule; the owner said 'loaded from the disk on rendering' without saying which layer reads it.
- (assumption) Assumed a non-embedded face is recorded as the existing chain-entry STRING (a face name), with no filesystem path anywhere in the .folio - a path would make the document machine-specific and is not something the owner asked for.
- (assumption) Assumed the disk source is an explicit directory the integrator names, not enumeration of the operating system's installed font book.
- (capability) CAP-1 - An author imports a font file from their own machine; the face enters the designer's local face store and becomes pickable on a chain exactly as a catalogue face is.
- (capability) CAP-2 - The document declares whether it embeds its faces, as a page-setup option on the main template, travelling as a document-settings command like locale and utcOffset.
- (capability) CAP-3 - The rendering host builds its FontSet from a directory on disk as well as the shipped set, so a named-but-not-embedded face resolves without the document carrying its bytes.
- (capability) CAP-4 - A face named by a chain, not embedded and not supplied, is painted in a shipped face and the substitution is reported, rather than refusing the render.
- (capability) CAP-5 - An embedded author-supplied face carries the licence identity its own binary declares, copied verbatim.
- (constraint) The engine never reads the filesystem. The disk source is host-side; the engine's font input stays folio8.FontSet.
- (constraint) No filesystem path is ever written into a .folio. A non-embedded face is a face NAME - the chain entry's existing string shape - so the document stays machine-independent and hand-editable (FR12/S9).
- (constraint) Fallback NEVER changes the typeface silently: every substitution carries a diagnostic naming the chain, the entry, the requested face and the face painted.
- (constraint) An embedded document is unchanged in every respect - byte identity, dedupe by sha256, stored whole, no save-time subsetting. This work adds a second mode, it does not alter the first.
- (constraint) The catalogue tier keeps its build-time licence allowlist and its admission gate. The no-licence-gate ruling is scoped to faces the AUTHOR supplies.
- (question) Turning embedding OFF on a document that already carries embedded faces - are the assets stripped on the next save, kept, or is the option refused while faces are embedded?
- (question) Does the designer tell the author, at authoring time, that this document will fall back on a host that lacks the face - or is the substitution only discoverable at render?
- (question) Does an author-supplied face install its family's other cuts (bold/italic/boldItalic) the way spec-install-all-face-cuts has a catalogue family install its four, or is a disk import exactly the one file picked?
- (question) Does allowing an EMPTY licenceText on an embedded face move the format version, given 2.0 currently requires the three fields on a chain-named embedded face?
- (question) Which shipped face is the fallback - a fixed one, the chain's own first shipped entry, or the coverage-resolved best among the shipped set?

- (question) BLOCKER FOR THE EMBED PATH, found 2026-09-20 in folio-go/internal/fontset/licencesignature.go:298 - RefuseContradictedLicence refuses any face whose OWN name table matches a copyleft or restricted signature, regardless of what is declared beside it (silence admits; a statement that matches a refuse-signature does not). An author-supplied face under such terms is therefore refused BY THE ENGINE at embed time, which contradicts the owner ruling that Folio takes no position on the terms of a face the author supplies. Three ways out, none of them chosen here: (a) the guard is scoped to Folio-distributed faces and an author-supplied face bypasses it; (b) the guard stands and the owner ruling is narrowed to mean 'we do not JUDGE, but we still refuse what we cannot redistribute'; (c) the guard stands and an author-supplied face under refused terms may be NAMED but never EMBEDDED. Needs an owner ruling before Story 5, and it shapes Story 3.
