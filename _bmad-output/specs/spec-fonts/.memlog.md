- (event) Spec folder created from the 2026-08-30 fonts conversation; capabilities CAP-1..CAP-4 assigned.
- (direction) User direction: show a list of freely-usable Google fonts in the designer and ship the referenced faces inside the saved .folio; user raised upgrading .folio to a zip of folders as a possible container.
- (note) Measured: the engine ships three Regular-only faces (Noto Sans 646KB, Noto Sans Thai 47KB, Noto Sans SC 10.6MB) embedded at build time by folio-go/fonts/fonts.go; a document's fonts map declares named chains over those face names, and the designer's starter.folio declares exactly one chain (body).
- (note) Measured: no command edits the fonts map, so every document created in the designer offers exactly one family; style.bold and style.italic are stored and projected but consumed by no producer, and no bold or italic face ships.
- (decision) No container change: .folio stays one JSON file, because the format's stated reason for being text is that a person or agent can edit it without the designer (FR12) and a hand-written template must render (S9); a zip also puts entry order, timestamps and compression inside the byte-identity regime and forces a MAJOR version break.
- (decision) Font bytes ride the existing content-addressed assets map (sha256 key, base64 hard-wrapped at 76 columns, dedupe by hash, stable emission order) rather than any new storage mechanism - images already prove the shape and AD-9 canonical serialization already covers it.
- (decision) A fonts-map chain entry may name a shipped face or an embedded asset key; chain semantics are unchanged (ordered, resolved per rune for coverage), so a chain can mix an embedded Latin face with a shipped CJK fallback.
- (decision) The designer's font catalogue ships inside the offline release bundle; the authoring path never calls fonts.google.com or fonts.gstatic.com, because the designer is offline-first with a service worker and verified asset URLs.
- (decision) An embedded face is stored whole - no save-time subsetting - because the report data changes between saves and a save-time subset would drop glyphs a later render needs; PDF subsetting stays where it is, per render, one subset per document.
- (decision) CJK stays on the shipped-face path by default and the embeddable catalogue is Latin/Thai-scale, because a full SC face is 10.6MB and would dominate a base64 JSON document.
- (decision) Every embedded face carries a licence record in the document, so a file that travels alone still states what it is redistributing (AD-26, and lint's licence check already governs shipped faces).
- (constraint) Render time reads no network and no host-installed font: a document that names an embedded asset must render from its own bytes alone (FR33).
- (constraint) Byte identity is unchanged: the same document saved twice, and rendered on any of the four targets, still produces identical bytes with fonts embedded.
- (capability) CAP-1 authorable font chains: create, rename, reorder and delete chains and their entries in the designer, over engine-validated names.
- (capability) CAP-2 embedded font assets: a .folio carries the faces its chains name, keyed by content hash, and renders on a machine that has never seen them.
- (capability) CAP-3 bundled font catalogue: the designer offers a curated, offline, freely-licensed catalogue that the author searches and picks from, and picking embeds.
- (capability) CAP-4 located failure for a broken font reference: an absent or undecodable font asset, or a chain naming neither a shipped face nor a present asset, is a located load error rather than a silent substitution.
- (assumption) Assumed the catalogue is restricted to OFL-licensed families, reading the user's 'can be used freely' that way.
- (assumption) Assumed the fields are additive and so a MINOR version bump, not MAJOR - flagged as an open question because the version rule is a load-time error path.
- (question) MINOR or MAJOR .folio version bump for the additive font-asset fields?
- (question) Which families make the shipped catalogue, how many, and who curates the list as it changes?
- (question) Do bold and italic get realized in this scope (they need real faces per weight and both producers wired), or stay explicitly out?
- (question) May an author embed a font file from their own disk, the way an image is imported, or is the catalogue the only source?
- (question) Does the licence record live inline on each font asset, or in one document-level notice block?
- (question) Is an embedded CJK face refused, warned about, or simply allowed at its full weight?

- (decision) D-8.1.1 (2026-08-31, Story 8.1): FR52's "reorder" is INAPPLICABLE at chain level and satisfied IN FULL at entry level - the verbs distribute over "chains AND THEIR ENTRIES" and `reorder` has a referent only in entries, because a chain is an ordered list and `fonts` is not. The absence of chain key order is load-bearing: folio-format.md reasons FROM it to kill the font-default idea, so adding one would reopen that question; chain order is also semantically inert (no byte, no lookup, no render) and the presentation need it might serve is designer UI state needing no format change. CAP-1's intent in SPEC.md was amended accordingly at `ac532c3`. The (capability) line above is left as originally assigned, because this log records what was decided when.
- (decision) OWNER 2026-09-20 - REVERSES D-8.6.1: an author MAY embed a font file from their own disk. The reversal is of the premise, not the mechanism - Folio takes no position on the terms of an author-supplied face, so nothing has to be invented. The three required licence fields are filled by copying the binary's own name records (ID 0, 13, 14) verbatim, empty where absent. The catalogue tier's build-time allowlist and fail-the-build gate (D-8.5.2/D-8.5.3) are untouched; the no-gate ruling is scoped to faces the AUTHOR supplies, not faces Folio distributes.
- (decision) OWNER 2026-09-20 - AMENDS the 'nothing fetched or read at render time' constraint: the rendering host may build its FontSet from a directory the integrator names. Still holds: no network at render time, no enumeration of the installed font book, no path inside the .folio, and the engine itself still never touches the filesystem (FontSet remains its only input).
- (decision) OWNER 2026-09-20 - AMENDS the 'No host fonts' non-goal: the word that survives is 'installed'. Neither side enumerates the OS font book; both may read a file a human pointed at - an author picking a file, an integrator naming a directory.
- (decision) OWNER 2026-09-20 - AMENDS CAP-4's success: the absent-asset-key load error is untouched; a NAMED face the renderer was not given no longer refuses the render but is painted in a shipped face with a diagnostic naming chain, entry, face requested and face painted. The guarantee becomes 'no SILENT substitution' rather than 'no substitution'.
