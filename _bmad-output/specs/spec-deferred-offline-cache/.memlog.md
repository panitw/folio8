topic: Cutting the designer's blocking first load by tiering the offline release into a guaranteed core and on-demand deferred assets

- (direction) Owner: the full offline designer makes first load too long and gives first-time users a bad experience; load in background or cache only what is needed.
- (note) Measured from dist/offline-release-manifest.json: release is 79 cache assets, 18.62 MiB Brotli over the wire, 55.9 MiB uncompressed; engine wasm 8.11 MiB, CJK font 4.72 MiB, 31 catalogue faces 3.01 MiB, pdf.js 0.29 MiB, examples+docs ~0.25 MiB, base fonts ~0.9 MiB.
- (note) engineMayStart() in folio-designer/src/offline-lifecycle.ts gates the whole app on cacheReady, which the worker only sets once every one of the 79 assets verifies; 100% of the release is blocking today.
- (note) spec-folio SPEC.md constraint still reads 'A ~9 MB first load is accepted' — stale by 2x against the measured 18.62 MiB; that constraint is what this spec revises.
- (decision) Tier the release: a guaranteed CORE (19 assets, 10.01 MiB) gates the designer; the remaining 60 assets / 8.61 MiB are fetched the first time they are actually needed and cached permanently. Chosen over background top-up because bandwidth for a user who never touches CJK or the catalogue is waste, not insurance.
- (decision) No background prefetch of the deferred tier. Deferred assets are fetched strictly on demand — one mechanism to build and test, and the first-load win is not re-spent on the same bytes arriving anyway.
- (decision) A document is preflighted on open: every asset it needs is checked up front, and an open that needs an uncached asset with no network is refused with the missing assets named, rather than failing later mid-edit.
- (decision) The tiering is fully automatic — no 'download everything' control and no cache-status surface for the author. Owner call: keep the surface simple.
- (constraint) Byte-identity is not negotiable for this change: a missing deferred font is refused, never substituted. Preview and canvas keep showing the real production output or nothing.
- (note) An on-demand fetch-and-keep tier already exists: folio-designer/src/font-store.ts keeps web-tier faces in IndexedDB, and font-browser-model.ts defines AVAILABLE LOCALLY as the committed catalogue plus the faces this designer fetched and kept.
- (constraint) Deferring the 31 catalogue faces changes what AVAILABLE LOCALLY means in the font browser: a catalogue face is no longer locally held just by shipping in the release. The label must stay truthful per-face rather than per-tier.
- (constraint) Release identity and verification must split with the tiers: cacheReady today means all 79 assets verified. A core-tier readiness signal is needed that does not claim the deferred tier is present, and the deferred fetch must use the running release's content-addressed URL so a pending release never mixes tiers.
- (constraint) The build-time bounds move with the split: minimumCacheAssets/maximumCacheAssets and warnCacheAssets in src/release-payload.ts, the S1 payload shape, and verify-offline-release.mjs all count one undifferentiated asset set today.
- (assumption) A catalogue face picked mid-session while offline is refused the same way a preflight miss is refused — the owner answered preflight-on-open, and the same rule applied mid-session is the consistent reading.
- (question) The engine wasm is 8.11 MiB of the 10.01 MiB core, so tiering alone halves the wait and no more. Is a 10 MiB gate acceptable, or does the engine need streaming compilation or its own split to reach an acceptable first load?
- (question) Is the CJK font deferred as a whole, or does a first-time CJK document become openable by fetching it at open time when the network is up — i.e. does preflight fetch, or only check?
