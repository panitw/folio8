- (decision) OWNER: the marshalling boundary is a POOL of engine threads, not one. Reason recorded: cgo runs a c-shared export ON THE CALLING THREAD rather than handing it to Go's scheduler, so a single thread would serialise every render in the process onto one core. Pool is sized to available parallelism (ProcessorCount-shaped), not a fixed small constant, and threads are reused - a fresh thread pays cgo's attach/detach cost on every crossing.
- (question) SPIKE, and it gates the pool design: does a thread the BINDING creates even get an adequate sigaltstack? On Linux the CLR installs one on every thread it owns, and a 'new Thread()' IS a CLR thread. If so, 'create our own thread' fixes nothing on its own and the fix must explicitly enlarge the signal stack on the pool threads (sigaltstack() via P/Invoke) or cross on a raw pthread the CLR never sees.
- (decision) Signal-stack sizing RESOLVED in principle: pick one generous fixed size (a few hundred KB per pool thread) rather than computing it. Reason: SIGSTKSZ is a compile-time constant before glibc 2.34 and a sysconf()-backed runtime value after, because modern register save areas (AVX-512) are large - so no single queried value is right on both, and the memory cost of over-provisioning is negligible.
- (decision) Former open question 3 RESOLVED, and half of it was wrong: the folio8 C ABI has NO callbacks - results are a buffer plus a token - so 'blocks inside a diagnostic callback' does not exist. What is real: folio8_free(token) is itself an ABI call, so a caller who renders on one thread and disposes on another crosses the boundary too. Requirement, not a question: EVERY crossing including free routes through the pool, so callers see no new restriction. The alternative - 'dispose on the thread you rendered on' - is rejected as a contract.

- (event) SPIKE RUN 2026-09-22, and it ANSWERS the gating question: NO. The CLR installs a fixed-size sigaltstack on every thread it touches - measured 24576 bytes on arm64 and 16384 on amd64 - identical for main, .NET TP Worker, new Thread() at any managed stack size, and a raw pthread once attached. Constant across .NET 6/8/9 and across glibc 2.31 (where sysconf(_SC_SIGSTKSZ) returns -1) and 2.36, so it is a CLR constant and tracks nothing. Probe preserved at evidence/Program.cs.
- (note) Mechanism completed at source, in the repo's PINNED Go 1.26.0: os_linux.go mpreinit allocates gsignal at 32*1024, but signal_unix.go minitSignalStack ADOPTS an existing altstack under cgo (setGsignalStack) instead of installing Go's own. The CLR always installs one, so Go's SA_ONSTACK handlers always run in the CLR's 16 or 24 KiB rather than Go's 32.
- (note) The spike EXPLAINS the amd64/arm64 asymmetry DW-396 recorded without an account: 16 KiB vs 24 KiB of headroom for the same handler frame. arm64 was never clear, only wider-margined - which is what this spec's 'absence is not evidence' rule already predicted.
- (note) Refines DW-396's glibc reading: the receiving buffer is a CLR constant and does not move; what varies is what goes into it (the kernel's signal frame, sized by the CPU's register state, plus the handler). So machine-to-machine variation is expected and a clean run on one box says nothing about another.
- (decision) FIX CONFIRMED in principle: explicit sigaltstack() enlargement via P/Invoke works (24 KiB -> 1 MiB, rc 0), and the runtime stays healthy afterwards - NullReferenceException still caught, full blocking GC completes. It replaces the CLR's altstack memory with MORE of it rather than removing it, so the CLR's own SIGSEGV handling is not deprived.
- (decision) The POOL SURVIVES and is now justified twice: throughput (cgo runs the export on the calling thread) AND as the only clean holder of the fix - a bounded set of long-lived threads whose signal stacks the binding sizes once at creation. But it is NOT sufficient alone: a pool of ordinary new Thread() workers would have reproduced the defect exactly. The load-bearing step is the sigaltstack enlargement.
- (constraint) The enlarged altstack memory must outlive the thread and must never be freed while that thread can take a signal, and it must be installed BEFORE the thread's first crossing because minitSignalStack adopts whatever it finds at needm time.
- (question) Confirm 16384 on REAL amd64 (the WSL2 box) and capture sysconf(_SC_SIGSTKSZ) there - the amd64 row in the spike was emulated. If sysconf exceeds 16384, the CLR's altstack is below what glibc itself calls a minimum on that machine.
- (question) DllImport("libc") for sigaltstack must resolve from the netstandard2.0/net46 floor. Plain P/Invoke, so it should - but pthread_create was NOT resolvable from libc on glibc 2.31 (it lived in libpthread until the 2.34 merge), so libc entry points are not uniformly available across the range this package supports.
