- (direction) Owner asked for a JavaScript library (folio-js) usable from Node.js, a .NET library (folio-dotnet) supporting .NET 4.6 through .NET Core, and documentation-site coverage of install, usage and API reference for both.
- (decision) Express mode: distill from the input plus the codebase, and record every unresolved fork as an open question rather than inventing an answer. Owner chose it over a guided field-by-field walk.
- (decision) Execution is HYBRID: folio-js runs the Go engine compiled to wasm under Node; folio-dotnet P/Invokes a c-shared native build of the same engine. Owner chose it because DllImport is the only engine-sharing route that reaches .NET Framework 4.6 - no wasm runtime targets it - and it keeps one engine, so byte-identity survives.
- (decision) API surface is RENDER + VALIDATE ONLY (parse template, render, render-to-stream, validate, diagnostics, fonts, data/params). Owner chose it over the full ~40-item Go surface; the canvas/designer command API stays out.
- (decision) Documentation gains ONE NEW PAGE PER LANGUAGE beside the existing rendering-library guide, rather than extending that guide or combining both languages onto one page.
- (constraint) Output must be byte-identical to folio8-go's for the same template, data, params and fonts on a given build toolchain; the fixtures/ golden corpus and its SHA-256s are the contract both libraries conform against. This is the project's central commitment and the reason a native port was rejected.
- (constraint) .NET floor is .NET Framework 4.6 - Windows-only, predates Span<T>, System.Text.Json and DllImportResolver, and has no wasm runtime - so the binding must be plain DllImport marshalling over a C ABI, with the managed assembly on netstandard2.0 to span 4.6 through modern .NET.
- (constraint) The determinism commitments carry over unchanged: no clock, no locale, no network, no filesystem beyond calls the caller makes, no ambient environment input. SOURCE_DATE_EPOCH stays a CLI-only convenience; library callers pass documentDate as an ordinary param.
- (constraint) docs/*.md is the source of truth and docs/*.html is the published page; both must be authored per new page. New .html pages must be registered in folio8-designer/scripts/build-wasm.mjs, must use system fonts only (the forbidden-font-hosts scan reds on remote font hosts), and spend release cache-asset slots against maximumCacheAssets=90.
- (note) Grounding: folio8-go is the reference engine with ~40 public items; folio8-go/wasm is the DESIGNER engine (Load/Apply command loop), not a render entry point, so folio-js needs its own wasm entry rather than reusing that shell.
- (capability) CAP-1 folio-js renders a PDF in Node from a template plus JSON data and params.
- (capability) CAP-2 folio-js validates a template against data and params and surfaces the engine's diagnostics.
- (capability) CAP-3 folio-dotnet renders a PDF from .NET Framework 4.6 through modern .NET on the supported platforms.
- (capability) CAP-4 folio-dotnet validates a template and surfaces the same diagnostics.
- (capability) CAP-5 Both libraries are proved byte-identical to folio8-go against the golden corpus in CI, on every supported runtime and platform.
- (capability) CAP-6 folio-js installs from npm with the wasm engine and the shipped font set resolved without a build step.
- (capability) CAP-7 folio-dotnet installs from NuGet and loads the right native binary per platform without caller configuration.
